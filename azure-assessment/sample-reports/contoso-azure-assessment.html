1. Network topology

Pattern identified Multi-region hub-and-spoke with exceptions High confidence

The network is built around 2 hub virtual networks (vnet-hub-eastus in eastus and vnet-hub-westeurope in westeurope), which host shared services: Azure Bastion, Azure Firewall and VPN gateway. 3 spoke networks peer to the hubs and carry the workloads. This is the hub-and-spoke pattern recommended in the Azure landing zone reference architecture: shared connectivity, inspection and management access are centralised in the hub, and workloads are isolated in spokes.

The regional hubs are peered with each other (global VNet peering), giving cross-region connectivity between spokes through their hubs.

Evidence from the inventory

  • Hub vnet-hub-eastus (eastus, Contoso-Connectivity): address space 10.0.0.0/22; services: Azure Bastion, Azure Firewall and VPN gateway; spokes: vnet-prd-eastus and vnet-dev-eastus.
  • Hub vnet-hub-westeurope (westeurope, Contoso-Connectivity): address space 10.10.0.0/22; services: Azure Firewall; spokes: vnet-prd-westeurope.
  • Spokes vnet-prd-eastus and vnet-prd-westeurope send Internet-bound traffic to the hub firewall through a 0.0.0.0/0 route. vnet-dev-eastus has no such route, so its outbound traffic bypasses central inspection.
  • vnet-prd-eastus (Contoso-Production) is peered directly with vnet-dev-eastus (Contoso-NonProduction), bypassing the hub.
  • vnet-dev-sandbox (uksouth, Contoso-NonProduction) is not peered to any network.

  • Decide whether vnet-dev-sandbox should join the hub or be removed; unmanaged islands tend to accumulate public exposure.

2. Hybrid connectivity

Pattern identified Site-to-site VPN to on-premises High confidence

The environment connects to on-premises through a site-to-site VPN, terminated in the hub network vnet-hub-eastus. Spokes use the hub gateway through gateway transit, which is the recommended shared-gateway design.

Evidence from the inventory

  • vgw-hub-eastus: Vpn gateway, SKU VpnGw2AZ, zone-redundant, active-standby, deployed in vnet-hub-eastus.
  • lng-onprem-dc1: on-premises site at 203.0.113.10 advertising 192.168.0.0/16.
  • cn-hub-eastus-to-dc1: IPsec connection, status Connected.

Considerations against the reference architecture

  • Only eastus has a gateway; spokes in westeurope reach on-premises across regions, and lose on-premises connectivity if that region is unavailable. Add a gateway in each regional hub.
  • A single VPN tunnel runs over the Internet; for production workloads with latency or bandwidth needs, consider ExpressRoute with VPN as backup.
  • Configure VPN gateways as active-active with two on-premises devices to remove a single point of failure.

4. Subscription and landing zone model

Pattern identified Landing-zone style: platform and workload subscriptions, split by environment Medium confidence

The 3 subscriptions in scope appear to play these roles: Contoso-Connectivity (platform: connectivity), Contoso-NonProduction (workload: non-production) and Contoso-Production (workload: production). Roles are inferred from subscription names, environment tags and the resources each contains.

Separating shared platform services (connectivity, management) from application workloads follows the Azure landing zone model in the Cloud Adoption Framework, where platform teams own the hub and workload teams own their subscriptions.

Workloads run on IaaS virtual machines and App Service web apps: 24 VM-based resources and 16 managed (PaaS) services. VMs make up the majority, so the estate is primarily IaaS; much of the operating system patching, scaling and availability work remains with the customer.

Tiers identified: presentation (Application Gateway and App Service), application (VMs and App Service) and data (SQL databases and SQL servers).

Evidence from the inventory

Considerations against the reference architecture

  • No VM scale sets are used, so VM capacity does not scale automatically. Stateless tiers are good candidates for scale sets or App Service.
  • Review VM-hosted components for replatforming to PaaS (App Service, Azure SQL, AKS) to reduce operational overhead.

6. Resilience and disaster recovery

Pattern identified Multi-region, but not in Azure region pairs; no DR replication evidence Medium confidence

Production runs in 4 regions (eastus: 36, westeurope: 24, uksouth: 10, centralindia: 7 resources). None of these regions are paired with each other. Running in several regions only provides disaster recovery if data is replicated and workloads can fail over; the inventory shows the building blocks, not a tested failover plan.

Within regions: 9 of 24 VMs use availability zones, 3 of 10 storage accounts replicate across zones and 4 replicate to a paired region, and 1 of 6 SQL databases is zone redundant.

Backup and site recovery: 0 vaults found, so there is no evidence of Azure Backup or Azure Site Recovery protecting these workloads.

Considerations against the reference architecture

  • Deploy Recovery Services vaults and back up VMs and databases; define RPO/RTO per workload.
  • Decide the DR strategy per workload (active/active, active/passive or backup-and-restore), then replicate data and test failover.
  • Place production VMs across availability zones (or use zone-redundant scale sets) to survive a datacenter failure.
